# 건축 설계 토탈 시스템 — 아키텍처 설계서 & 1차 구현 지시서

> Part A는 전체 시스템의 뼈대 설계다. Part B는 클로드코드에 바로 넘길 1차 구현 지시서다.
> **Part A를 읽지 않고 Part B만 실행하지 말 것.** 1차 구현물이 전체 구조에 맞물리도록 설계되어 있다.

# Part A. 전체 시스템 설계

## A-1. 이 시스템의 본질

사용자가 원하는 것은 13단계 워크플로가 아니다. **하나의 프로젝트 상태를 여러 모듈이 각자의 방식으로 읽고 쓰는 구조**다. "순서대로가 아니라 복합적·상호작용적으로"라는 요구는 곧 이런 뜻이다.

따라서 시스템을 단계의 연쇄(step 1 → step 2 → …)로 짜면 반드시 실패한다. 대지가 바뀌면 사업성이 무너지고, 사업성 때문에 규모를 줄이면 매스가 바뀌고, 매스가 바뀌면 평면과 렌더가 전부 무효가 되기 때문이다.

**올바른 구조: 중앙에 프로젝트 상태(Project State)가 있고, 모든 모듈은 그 상태를 읽어 자기 산출물을 만들고 다시 상태에 기록하는 위성이다.**

```
                    ┌─────────────────────┐
        M1 대지 ────▶│                     │◀──── M4 매스 스터디
       M2 법규 ─────▶│   PROJECT STATE     │◀──── M5 조닝·스케치
     M3 사업성 ─────▶│   (단일 진실 원천)   │◀──── M6 평면
                     │                     │
        M9 리포트 ◀──│  + 의존성 그래프     │────▶ M7 뷰포트·렌더 ★1차 구현
       M10 미디어 ◀──│  + 무효화 플래그     │────▶ M8 도면·BIM
                    └─────────────────────┘
```

## A-2. 프로젝트 상태 모델 (스키마 초안)

이 스키마를 **가장 먼저** 확정해야 한다. 이게 흔들리면 모든 모듈을 다시 짜야 한다.

```ts
type ProjectState = {
  meta: { id, name, createdAt, activeScenarioId }

  site: {
    parcels: Parcel[]           // 개별 필지 (PNU, 지목, 면적, geometry)
    operation: 'single' | 'merge' | 'custom'   // 단필 / 합필 / 임의 경계
    boundary: GeoJSON.Polygon   // 최종 대지 경계 (합필·개발 후 결과)
    area: number                // 대지면적 (㎡)
    roads: { width: number, side: string }[]   // 접도 조건
    slope: { min, max, avg }    // DEM 기반
    notes: string
  }

  regulation: {
    useZone: string             // 용도지역
    useDistrict: string[]       // 용도지구·구역
    dpUnitPlan: {               // 지구단위계획
      applies: boolean
      documentRefs: DocRef[]    // 지침 PDF 출처 + 페이지
      conditions: Condition[]
    }
    bcr: { legal: number, applied: number }    // 건폐율
    far: { legal: number, incentives: Incentive[], applied: number }  // 용적률
    heightLimit: { type, value, basis }
    setbacks: Setback[]
  }

  program: {
    uses: { code: string, name: string, ratio: number }[]  // 복합용도 대응
    grossArea: number
    unitMix?: { type, count, exclusiveArea }[]   // 세대·호실
    efficiency: number          // 전용률
    parking: { legal: number, recommended: number, basis: string }
  }

  feasibility: {
    landCost, constructionCost, softCost, financeCost
    revenue: { sale, rent }
    assumptions: { vacancyRate, capRate, discountRate, ... }
    results: { totalCost, NPV, IRR, ROI }
  }

  massing: {
    scenarios: MassScenario[]   // 대안 여러 개
    floorTable: FloorArea[]     // 층별 면적표
    modelRef?: string           // glb 참조
  }

  design: { zoning, sketches, floorPlans, materials }

  outputs: { renders, reports, drawings, media }

  provenance: ProvenanceEntry[]   // 모든 숫자의 근거 추적
}
```

**`provenance` 필드가 이 시스템의 신뢰도를 결정한다.** "용적률 250%"라는 숫자가 어느 조례 몇 조에서 나왔는지, AI 추정인지 법령 원문인지, 사용자가 수동 입력한 값인지를 항상 함께 저장한다. 근거 없는 숫자는 실무에서 쓸 수 없다.

## A-3. 의존성 그래프와 무효화

각 모듈은 자기가 어떤 상태 필드에 의존하는지 선언한다. 의존 필드가 바뀌면 산출물에 **`stale` 플래그**를 세우고 UI에서 흐리게 표시한다. 자동 재계산은 하지 않는다 — 사용자가 "재검토" 버튼을 눌러야 한다.

예: `site.boundary` 변경 → `regulation`, `program.parking`, `feasibility`, `massing`, `outputs.renders` 전부 stale.

이 무효화 체계가 없으면, 대지를 수정한 뒤에도 옛 사업성 숫자가 리포트에 그대로 실려 나간다. 실무에서 가장 위험한 종류의 오류다.

## A-4. 대안(시나리오) 관리

건축 기획의 본질은 대안 비교다. 상태 모델은 처음부터 **시나리오 분기**를 지원해야 한다.

- 시나리오 = `program` 이하의 스냅샷 (대지·법규는 공유)
- "용도 비율 A안 vs B안", "최대규모안 vs 사업성최적안" 비교 테이블
- 시나리오별 렌더·리포트 독립 생성

## A-5. 절대 원칙 — 계산은 코드, 판단은 AI

이 시스템에서 가장 중요한 규율이다.

| 반드시 결정론적 코드로 | AI에게 맡겨도 되는 것 |
|---|---|
| 용적률·건폐율 계산 | 지구단위계획 지침 PDF에서 관련 조항 찾기 |
| 주차 법정대수 | 스페이스 프로그램 초안 제안 |
| 사선제한·일조 검토 | 매스 대안 아이디어 생성 |
| 면적표 집계 | 리포트 문장 작성 |
| 사업성 재무 계산 | 이미지 리터칭·다이어그램 |

**용적률을 LLM에게 계산시키지 말 것.** 조항을 찾아오게 하고, 계산은 룰 엔진이 한다. 법규 판단 결과는 항상 "참고자료이며 최종 확인은 담당 건축사 책임"으로 명시한다.

## A-6. 데이터 소스

| 필요 데이터 | 출처 | 비고 |
|---|---|---|
| 지적도·필지 | 브이월드 Data API | 합필 시 geometry union 직접 처리 |
| 용도지역·지구 | 브이월드 / 토지이용계획 API | |
| 지형(DEM)·3D 건물 | 브이월드 WebGL 3D API | 저장·캐싱 금지 (보안규정) |
| 건축물대장 | 국토부 공공데이터 API | 기존 건물 정보 |
| 공시지가·실거래가 | 국토부 API | 사업성 입력값 |
| 법령·조례 | 국가법령정보센터 API | 자치법규 포함 |
| 지구단위계획 지침 | **자동화 불가 — PDF 수동 수집 후 RAG** | 최대 난관 |

지구단위계획 지침은 지자체마다 형식이 제각각인 PDF다. 전국 대응은 불가능하다. **회사가 주로 일하는 지역 2~3곳부터** 수동으로 수집해 시작할 것.

## A-7. 모듈별 난이도 판정

솔직하게 구분해둔다. 여기를 잘못 잡으면 프로젝트가 중간에 멈춘다.

**지금 기술로 확실히 되는 것**
- M1 대지 (합필·임의 경계 포함)
- M2 법규 규모 검토의 **계산부** (건폐율·용적률·주차·개략 사선)
- M3 사업성 검토 — 사실상 잘 만든 계산기다
- M7 뷰포트·렌더 ★1차 구현 대상
- M9 리포트 생성

**되지만 검증이 많이 필요한 것**
- M2의 지구단위계획 해석 — RAG 품질에 좌우됨
- M4 매스 대안 AI 추천 — 형태 생성이 아니라 규칙 기반 대안 + AI 설명 조합으로 접근
- M5 조닝·스케치 인터랙션 — UI 난이도가 높음
- M10 다이어그램·영상

**현시점에서 목표를 낮춰야 하는 것**
- M6 정밀 평면도 자동 생성 — 초안 다이어그램 수준까지가 현실적
- M8 허가도서 DWG/BIM 자동 생성 — **전체 도면 세트 자동 생성은 실무 품질에 못 미친다.** 현실적 대안: ① 필요 도면 리스트 자동 산출 ② 표제부·면적표·주차계획표 등 표 기반 도면 자동화 ③ 평면은 IFC 내보내기로 Revit/ArchiCAD에 넘겨 사람이 마무리

허가도서는 법적 책임이 따르는 문서다. 자동 생성물은 예외 없이 초안으로 취급하고 건축사 검토를 거치는 절차를 시스템에 강제로 넣을 것.

## A-8. 권장 구축 순서

단계 번호 순서(1→13)로 만들지 말 것. 아래 순서가 훨씬 안전하다.

1. **상태 스키마 + 저장소 확정** (며칠)
2. **M7 뷰포트** ← 지금 만들 것. 눈에 보이는 결과가 나와야 조직이 움직인다
3. **M1 대지 + M2 계산부** — 스키마의 뼈대를 실제로 채워보는 단계
4. **M3 사업성** — 여기까지 오면 이미 사내에서 쓸 수 있는 도구가 된다
5. M4 → M5 → M9 순으로 확장
6. M6·M8·M10은 위 5개가 안정된 뒤에 재평가

# Part B. 1차 구현 지시서 — M7 뷰포트·렌더 모듈

## B-0. 이 모듈의 위치

전체 시스템의 **M7 모듈**을 독립 실행 가능한 형태로 먼저 만든다. 단, 나중에 통합할 수 있도록 아래 두 가지를 반드시 지킨다.

1. 모든 입력값(대지 경계, 좌표, 건물 정보)은 **`ProjectState` 형식의 JSON 객체 하나**에서 읽어온다. 지금은 그 객체를 UI 입력이나 로컬 파일에서 만들지만, 나중에는 M1~M6이 채워준다
2. 산출물은 `state.outputs.renders[]`에 기록하는 형태로 저장한다 (카메라 좌표, 프롬프트, 시각, 이미지)

**하드코딩된 전역 변수로 대지·건물 정보를 다루지 말 것.** 이 규칙 하나가 나중에 몇 주를 아낀다.

## B-1. 목표

주소를 입력해 대지 주변 3D 지형(콘타)을 불러오고, SketchUp에서 뽑은 glb를 그 위에 올린 뒤, 원하는 각도에서 캡처해 **건물 형태는 그대로 유지한 채** 재질·하늘·조경·인물·빛만 사실적으로 입힌 이미지를 얻는다.

핵심 원칙: **AI는 형태를 만들지 않는다. 형태는 3D 뷰가 결정하고 AI는 리터칭만 한다.**

## B-2. 기술 스택

- Next.js (App Router) + TypeScript + Tailwind CSS
- 브이월드 웹지엘 3D지도 API 3.0 — CesiumJS 기반이며 별도 Cesium 스크립트 선언 없이 Cesium 기능 사용 가능
- 서버 라우트(`app/api/*`)를 프록시로 사용. API 키는 절대 클라이언트에 노출 금지
- 상태 관리 Zustand. 초기에는 DB 없이 상태 JSON 내보내기/불러오기로 처리

```
# .env.local
VWORLD_API_KEY=
VWORLD_DOMAIN=localhost
OPENAI_API_KEY=
```

## B-3. 화면 구성

좌측 패널 + 우측 3D 뷰포트.

1. `대지` — 주소 검색, 필지 표출, 콘타 간격
2. `건물` — glb 업로드, 위치·회전·고도 조정
3. `뷰` — 카메라 프리셋 저장, 날짜/시간 그림자
4. `렌더` — 리터칭 옵션, 생성, 결과 갤러리

우측 하단에 현재 카메라 좌표·고도·방위 표시.

## B-4. 단계별 구현

각 Phase가 끝날 때마다 동작을 확인하고 넘어갈 것. 한 번에 전부 짜지 말 것.

### Phase 0 — 상태 스키마
Part A의 `ProjectState` 타입을 `types/project.ts`에 정의한다. 이 모듈에서 실제로 쓰는 필드는 `site`, `massing.modelRef`, `outputs.renders`뿐이지만, **타입 전체를 미리 선언해둘 것.**

### Phase 1 — 지형과 대지
- 브이월드 3D API 3.0 로드 및 초기화
- 주소 검색(Search API) → 좌표 이동
- 연속지적도 레이어로 필지 폴리곤 표출 → `state.site.parcels`에 저장
- **복수 필지 선택 및 합필**: 클릭으로 여러 필지를 선택하면 geometry union으로 `state.site.boundary` 생성 (turf.js 사용). 합필 면적 자동 합산
- 등고선: Cesium `ElevationContour` 머티리얼, 간격(1/5/10m)·색상 조절
- 주변 3D 건물 레이어 on/off

> 브이월드 API는 CORS 때문에 검색·데이터 요청을 브라우저에서 직접 호출하면 막힌다. 반드시 `app/api/vworld/*` 서버 라우트를 경유시킬 것. 지도 타일·스크립트 자체는 클라이언트에서 직접 로드한다.

### Phase 2 — 건물 배치
- glb/gltf 드래그앤드롭 (Blob URL, 서버 업로드 불필요)
- 초기 위치는 `state.site.boundary` 중심
- 조정 UI: 경위도 미세이동, heading 회전, 고도 오프셋(±50m), 스케일
- "지형에 스냅" — 해당 좌표 지형 고도를 샘플링해 바닥 정렬
- SketchUp 원점이 다를 수 있으니 오프셋 수동 보정 가능하게

### Phase 3 — 2패스 캡처 (이 모듈의 핵심)

같은 카메라에서 **두 장**을 뽑는다.

**A패스 — 뷰티 캡처 (AI 입력)**: 건물 무광 흰색, 그림자 활성화, 지형은 저채도. 형태와 입체감이 또렷할수록 AI가 형태를 잘 따라간다.

**B패스 — 실루엣 캡처 (마스크용)**: 카메라 고정한 채 건물만 단색(마젠타)으로 컬러 리플레이스, 나머지는 어둡게. 임계값 처리로 건물 영역 마스크 생성.

**마스크 규칙**: OpenAI Edits 엔드포인트는 **투명 영역을 수정 대상**으로 본다. 건물 영역은 불투명(보존), 배경·하늘·주변은 투명(수정 허용). 실제 동작은 소규모 테스트로 확인하고 반전 토글을 둘 것.

**기술 주의**: Cesium 캔버스 `toDataURL()`에는 WebGL `preserveDrawingBuffer: true`가 필요하다. 브이월드 래퍼가 이 옵션을 노출하지 않으면 `scene.postRender` 이벤트 안에서 캡처하는 방식으로 우회할 것.

### Phase 4 — AI 리터칭

`app/api/render/route.ts`에서 OpenAI 이미지 API 호출 (모델 `gpt-image-2`, Edits 엔드포인트, 이미지 + 마스크).

사용자 입력: 외장 재료, 시간대, 계절, 분위기, 추가 지시. 서버에서 아래 템플릿으로 조립:

```
Photorealistic architectural visualization of the building in the input image.

CRITICAL CONSTRAINT: Preserve the building's geometry, mass proportions,
floor count, roof shape, window and opening layout, and the camera angle
```

- 한 번에 2~3장 변형 생성 후 비교 선택

# Part C. 벤치마크 분석 — CAI Canvas

경쟁 제품(2026년 건축공간디자인페어 출품)의 구성을 관찰한 결과와, 그로부터 도출한 우리의 전략.

## C-1. 관찰된 모듈 구성

| 모듈 | 기능 |
|---|---|
| PLANNERS | 대지 조건 입력 → 다중 AI 페르소나(경제학자·수석엔지니어 등) 토론으로 기획 방향 도출 + 인사이트 대시보드(토지이용계획 자동 조회, 건폐율/용적률/최대건축면적/최대연면적/허용층수 자동 산출) |
| CADASTRALMAP | 지적도·위성 배경 전환, 스케일, 그리드 모듈(1/3/10m), 방위 회전, Export |
| PLAN (Sketch to Plan) | WP 지점으로 건물 외곽선 설정 → 손그림 조닝(shop/core/cafe) → AI가 정식 평면 다이어그램으로 정리, 건폐율 실시간 표시 |
| 3D VIEW (Mass Studio) | 층고·층수 입력으로 커스텀 매스 생성, 건폐율/용적률 실시간 검증 |
| IMAGE | 3D 뷰 위에 손스케치 + 프롬프트(층별 재료) → 포토리얼 렌더. 결과 위에 다시 스케치 → 재생성 루프 |
| ELEVATION | 입면 지점 설정, 층수·면별 가시성 제어 → 입면 생성 |
| 2D DRAWING | 입면도 세트 자동 생성 |
| CHANGE VIEWPOINT | 조감/스트리트/코너/정면/디테일 뷰 전환 |
| PRINT | 리포트 / 도서 / 패널 / 영상, 페이지 수 지정 출력 |

## C-2. 가장 중요한 발견 — 노드 캔버스

이들은 전체를 **노드 그래프 캔버스**로 묶었다. 각 산출물이 노드가 되고 선으로 연결된다. "순서대로가 아니라 복합적·상호작용적으로"라는 요구의 정답이 이것이다.

이는 Part A의 상태 모델을 대체하는 게 아니라 **A-3 의존성 그래프에 UI를 입힌 것**이다. 우리도 같은 방향으로 간다.

```ts
type Node = {
  id: string
  type: 'site' | 'planners' | 'plan' | 'mass' | 'render' | 'elevation' | 'report'
  inputs: string[]          // 상류 노드 id — 이게 곧 의존성 그래프
  params: Record<string, unknown>
  output: unknown
  stateSnapshot: Partial<ProjectState>   // 생성 시점의 상태
  stale: boolean            // 상류가 바뀌면 true
}
```

노드가 상태의 스냅샷을 함께 들고 있어야, 상류를 수정했을 때 "이 렌더는 옛 대지 조건으로 만든 것"임을 알 수 있다.

## C-3. 그들이 택한 지름길과 그 대가

관찰된 흐름을 보면 **형태의 진실 원천이 이미지다.** 평면은 손스케치를 AI가 정리한 다이어그램이고, 입면과 렌더는 별도로 생성된 이미지다. 세 가지가 서로 정합한다는 보장이 없다.

데모에서는 드러나지 않지만 실무에서는 첫 주에 드러난다. 면적표와 평면이 안 맞고, 층수를 하나 바꾸면 평면·입면·렌더를 전부 다시 만들어야 하며, 그 결과가 또 서로 안 맞는다.

**우리의 차별점은 여기다.** Part B에서 이미 지오메트리를 진실 원천으로 잡았다(2패스 캡처, 형태 보존 리터칭). 느리지만 실무에서 살아남는 방식이다.

절충안: 컨셉 단계 노드는 이미지 루프를 허용하되, 노드 타입마다 **정합 보장 / 미보장 배지**를 표시한다. 미보장 노드의 산출물은 리포트·도서에 자동 포함되지 않게 막는다.

## C-4. 배울 것 — 구체적으로

- **실시간 지표 표시.** 매스를 조작하는 동안 건폐율·용적률이 계속 갱신된다. 우리 룰 엔진 결과도 항상 화면에 떠 있어야 한다
- **WP 지점 좌표 표기.** 손스케치 꼭짓점에 (0,0)/(85,70) 같은 좌표를 붙여 치수를 부여한다. 이미지 기반의 약점을 보완하는 영리한 장치인데, 우리는 이걸 아예 실제 지오메트리로 받으면 된다
- **그리드 모듈과 방위 회전.** 건축가가 실제로 손대는 컨트롤이다
- **이미지 위 손스케치 → 재생성 루프.** 이건 반드시 넣어야 한다. 설계자가 AI와 대화하는 가장 자연스러운 방식이다
- **뷰포인트 프리셋**과 **목적별 출력(리포트/도서/패널/영상)**

단, **화면 구성을 그대로 옮기지 말 것.** 우리 실무 흐름에 맞춰 재설계한다.

## C-5. "사내용이라 법적 문제 없다"는 사실이 아니다

가격 정책은 확실히 안 만들어도 된다. 하지만 나머지는 남는다. (변호사·변리사가 아닌 정리이므로, 판단이 필요한 항목은 전문가 확인 필요)

1. **브이월드 이용약관·보안** — 사내 시스템도 API 사용 등록 대상이다. DEM 저장·캐싱 금지 조항 확인 필수
2. **발주처 데이터 외부 전송 — 가장 큰 실무 리스크.** 미공개 프로젝트의 지번, 대지 조건, 설계안 이미지가 OpenAI 서버로 나간다. 발주처와의 비밀유지 약정에 저촉될 수 있다. 대응: 회사 보안 규정 확인 → 필요 시 발주처 동의 → 민감 프로젝트는 지번·좌표 마스킹 또는 로컬 모델 옵션. **이건 코드 짜기 전에 확인해야 한다. 답에 따라 아키텍처가 달라진다**
3. **API 계정은 회사 명의로.** 개인 키로 사내 도구를 돌리면 나중에 반드시 문제가 된다
4. **생성물 책임.** 법규 검토·면적표가 심의 자료로 흘러 들어가는 순간 책임이 발생한다. 건축사 검토 없이는 외부 반출이 안 되는 절차를 시스템에 넣을 것
5. **특허.** 경쟁사가 관련 출원을 했을 수 있다. 사내 업무 사용도 특허법상 '업으로서의 실시'로 볼 여지가 있어 완전 무위험은 아니다. 판매를 검토하는 시점에는 변리사 상담이 필수다

## C-6. 판매 가능성을 열어두려면 지금 해둘 것

아래는 지금 하면 추가 비용이 거의 없고, 나중에 하면 전면 재작성이다.

- API 키를 **테넌트 단위로 분리**할 수 있는 구조 (지금은 테넌트가 하나뿐이어도)
- **데이터 소스 어댑터 인터페이스** — 브이월드 호출을 직접 박지 말고 `SiteDataProvider` 인터페이스 뒤에 둘 것
- **법규 룰을 코드가 아니라 데이터로** (JSON/YAML) — 지자체 추가가 배포 없이 가능해진다
- 사용량 로깅, 상태 스키마 버저닝

다만 냉정하게: 사내 도구를 상품으로 바꾸는 비용은 대개 기능 개발보다 크다(지원, 온보딩, 보안 감사, 계약, SLA). **판매 판단은 사내에서 6개월 이상 실사용된 뒤에** 하는 게 맞다.

## C-7. "한 달이면 될 것 같다"에 대하여

기술적으로는 맞을 수 있다. 다만 **데모 품질과 실무 품질은 다르다.** 페어 데모는 잘 고른 대지 하나로 돌린다. 사내 도구는 아무 지번이나 던져도 안 죽어야 하고, 틀린 숫자를 한 번 내면 그날로 아무도 안 쓴다.

한 달을 잡되 범위를 **M7 + M1 + M2 계산부**로 좁힐 것. 9개 모듈을 얕게 만들면 아무도 쓰지 않고, 3개를 제대로 만들면 매일 쓴다.
